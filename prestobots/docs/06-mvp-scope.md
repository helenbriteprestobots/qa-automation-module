# Chatbot Testing Platform — MVP scope

> What the first version of the testing platform will and won't do. Written for everyone,
> technical or not. Terms are explained in the dictionary in
> [05-chatbot-testing-simple.md](05-chatbot-testing-simple.md).

---

## 1. Goal

A web page, **the platform**, where non-technical admins can:

1. **Create test cases**: the AI proposes them automatically, and admins can also describe one in their own words.
2. **Run them** with one click.
3. **See a detailed report** of every run.
4. **Create Jira cards** for anything that failed.

No coding and no QA team. One command starts the platform, and after that everything is done from the web page.

**What gets tested:** only the **Cauce chatbot** (repo `prestobotsv3`, product Salud), on
**salud-stage**, inside a dedicated **QA clinic**. Never the real system.

**Where it runs:** for the MVP, the platform runs **locally** on one computer and opens at
`http://localhost`. It isn't deployed anywhere and has no login. The code lives in a **private** repo.
Hosting it in the cloud comes after the MVP (see section 4).

## 2. The four MVP features

### 2.1 Test cases

A **test case** is a short patient story plus the things that must be true at the end.

| Field | Example |
| --- | --- |
| ID (automatic, never changes) | `SAL-BOOK-003` |
| Title | Patient books a cardiology appointment |
| Area | Booking |
| Story (plain Spanish) | *Un paciente saluda, pide turno con cardiología, elige el primer horario disponible y confirma.* |
| Checks | The bot replied every time · the bot offered the WhatsApp form (filling it is not automatable yet, see doc 07 B3) · the appointment exists in Macena · the AI judge agrees the patient was told the date and time |
| Origin | Generated from the bot design / Written by an admin / Changed by an admin |
| Status | **Proposed** → **Active** → **Archived** |

Admins never see code. The technical version of each test, the steps the runner actually
performs, is kept behind the scenes and generated by the AI.

#### a) Automatic creation (the main way)

- The admin clicks **"Generate test cases"**.
- The platform learns what the bot can do from:
  - **exploring the bot**: it says "Hola" and taps through the menus. It never types, and never taps
    options that could book, confirm or cancel an appointment, or hand the chat over to staff;
  - the WhatsApp form files in the chatbot code;
  - later, the bot's conversation design: the exported Dialogflow CX agent *Cauce V3* file,
    requested from the developers in doc 07.
- The admin sees what was found and the estimated AI cost, and clicks **Continue**.
- It proposes stories for everything the bot can do that isn't tested yet.
- Before showing a proposal, the platform **tries it twice**. Proposals that fail or give
  inconsistent results are flagged.
- Proposals appear in a **"To review"** list. The admin reads each one and clicks
  **Approve** (it becomes Active) or **Reject**, optionally with a reason. The AI never proposes a
  rejected idea again.

#### b) Manual creation, in natural language (when needed)

- The admin clicks **"New test case"** and writes what they want, in their own words:
  *"Probá un paciente que quiere cancelar el turno de mañana pero escribe en inglés."*
- The AI turns it into a test case (title, story, checks) and shows it as a preview.
- The admin can:
  - adjust it by writing again (*"also check that the bot offers to reschedule"*);
  - click **"Try it"** to run it once;
  - click **Save**.
- Editing an existing test case works the same way: describe the change in words.

### 2.2 Running tests

- **Manual start:** on the platform, choose what to run (one test case, a few, a whole area,
  or *everything Active*) and click **Run**.
- **Live progress:** each test case shows ⏳ waiting / ▶️ running / ✅ passed / ❌ failed / ⚠️ couldn't run.
- **Expected time:** each test takes about 1–3 minutes, because the bot answers through WhatsApp
  services in real time. Tests run a few at a time.
- **Safety:** before starting, the runner checks it's pointing at salud-stage and the QA clinic.
  If not, it refuses to run.
- **Run history:** every run is kept with its date and time.
- **One run at a time:** the MVP doesn't handle two runs at once. The Run button waits until the current run finishes.
- **Keep the platform open:** because it runs locally, a run only continues while the computer is
  on and the platform is running.

### 2.3 Run report

**Summary of the run**
- Passed / failed / couldn't run, total time, start time, the version of the chatbot that was tested.
- A short AI-written summary in plain words. Example: *"Everything works except cancelling from a
  reminder: the bot replies but the appointment stays active in Macena."*

**Detail of each test case**
- **Conversation view:** the whole chat shown like WhatsApp bubbles (patient vs bot), including buttons and forms.
- **Checks:** each one with ✅ or ❌, and what was expected vs what happened.
- **AI judge:** its verdict on the bot's replies and the reason, in plain words.
- **Likely cause** (AI-written, failed tests only): for example, the bot didn't understand, Macena
  rejected the booking, the bot took too long, or the test platform itself had a problem.
- **Technical details** (collapsed, for developers): message timestamps, conversation ID, raw errors.

**Comparison:** each test case shows its recent history (*"passed the last 12 runs, failed today"*),
so new problems stand out.

### 2.4 Jira cards

- Every failed test case has a **"Create Jira card"** button.
- The AI pre-fills the card, and the admin can edit it before sending:
  - **Type:** **Bug** or **Task**. The AI suggests one and the admin can change it:
    - **Bug** when the chatbot misbehaves;
    - **Task** for anything else that needs doing, such as setting up test data or a question to the developers.
  - **Title:** `[SAL-REM-001] Cancelling from a reminder doesn't cancel the appointment in Macena`
  - **Description:**
    - what the patient did, step by step;
    - what was expected and what happened;
    - the likely cause;
    - the full conversation (the report runs locally, so a link would only work on this computer).
  - **Assignee:** none. The team assigns it in Jira.
  - **Labels / priority:** taken from the platform settings, plus a label with the test case ID (e.g. `SAL-REM-001`).
- **Avoiding duplicates:** the platform remembers which cards it created for each test case. When
  creating a new one, it shows the earlier cards and lets the admin choose between a **new card** and
  **adding a comment** to an earlier one.
- **No status sync:** after a card is created, the platform keeps only its link. It doesn't read
  or follow the card's status in Jira.

### 2.5 AI budget

The platform uses the Claude API to write test cases, judge replies, explain failures and draft
Jira cards. To keep costs under control:

- **Settings:** the admin sets a **monthly budget** in USD.
- **Always visible:** a legend in the page header, e.g.
  **"Claude API: US$ 12.40 of US$ 50 this month · updated 2 h ago"**.
- **How it's counted: real spend from the Claude account, plus the platform's own recent calls.**
  1. **Real spend.** The platform reads the account's real cost from Anthropic's
     **Usage and Cost API** (`/v1/organizations/analytics/cost`) for the current month.
     - It catches spend from **anything** using the account, not only this platform.
     - It can show this platform's API key separately from the whole account.
     - It checks about once an hour.
  2. **Filling the gap.** Anthropic's figures arrive **4 to 24 hours late**. For the hours not
     covered yet, the platform adds its own calls: each records its tokens and is converted to
     dollars with Claude's price list.
     - The legend therefore shows *real figure up to X + estimate since X*, and says how old the real figure is.
  3. **Without an admin key** (see below), the legend falls back to counting only the platform's
     own calls and says so.
- **What this needs:** an **Admin API key** from the Claude Console.
  - Only an organization admin can create it.
  - It's a different key from the normal one: it can read costs but can't talk to Claude.
  - Individual (non-organization) Console accounts may not have the Admin API. If so, the
    account must be turned into an organization in the Console settings.
  - ⚠️ An admin key can also manage members and API keys, so it stays in the local `.env` file
    and the platform only ever uses it to **read** costs.
- **The budget amount itself** is set in the platform's settings. Reading the spend limit
  configured in the Console isn't generally available through the API yet.
- **Warning at 80%:** the legend turns yellow.
- **At 100%:**
  - AI features stop: no more generating test cases or judging replies.
  - Tests still run with their hard checks only, and the report says the AI judge was skipped.
  - The admin can raise the budget in settings.
- **Also recommended:** set a spend limit on the API key itself in the Claude Console, as a hard
  backstop the platform can't overrun.

## 3. Who uses it

For the MVP there's **one kind of user**: whoever runs the platform on their computer. That person
can do everything: create, approve, run, read reports and create Jira cards. Developers read the
Jira cards, which carry the whole conversation and the technical details.

**No login** for the MVP. Only people with access to that computer can use it. Login and roles
come back when the platform is hosted.

## 4. Out of scope for the MVP (later phases)

| Not in MVP | Why later |
| --- | --- |
| Scheduled automatic runs (nightly) | Manual runs first; adding a schedule is small once runs are stable |
| Runs triggered by each code change (PR) | Needs integration with the developers' GitHub workflow |
| Tests repairing themselves after intended bot changes | Needs run history first. In the MVP the AI explains the failure and the admin edits the test in words |
| Learning test cases from real patient chats | Privacy decision pending |
| Coverage map | Nice to have; the "Generate" button already covers gaps |
| Testing the legacy bot (`prestobots-master`), the Turnos bot, or the landing page | MVP is the Cauce chatbot only |
| Free "explorer" agent that chats looking for problems | After the MVP is stable |
| Testing on a real phone | Not needed (see doc 05, section 2) |
| Automatic Jira cards without a human click | Avoids noise. Admins decide what becomes a card |
| Following Jira card status from the platform | Not needed yet. The platform only keeps the card link |
| Hosting in the cloud, login with Google, roles | MVP runs locally. Next step after the MVP, on our own cloud account |
| Several runs at the same time | One at a time is enough for now |

## 5. How it's built (short technical note)

```
 ┌──────────────── The platform (web page on localhost) ─────────────────────┐
 │  Test cases · Run button · Reports · Jira button · AI budget legend       │
 └──────────────┬───────────────────────────┬────────────────────────────────┘
                │ "run these"               │ create card
                ▼                           ▼
        ┌───────────────┐              ┌─────────┐
        │  The runner   │              │  Jira   │
        │ (background)  │              └─────────┘
        └──┬─────┬───┬──┘
  fake msgs│     │   │ check appointments            ┌──────────────────────┐
           ▼     │   ▼                               │ Claude (AI):          │
 ┌──────────────┐│ ┌────────────────────┐            │ writes test cases,    │
 │ Chatbot on   ││ │ Macena testing API │            │ judges replies,       │
 │ salud-stage  ││ └────────────────────┘            │ explains failures,    │
 └──────────────┘│ read replies (read-only)          │ drafts Jira cards     │
                 ▼                                   └──────────────────────┘
          salud-stage database
```

Recommendations, to be confirmed by the developers:

| Piece | Recommendation |
| --- | --- |
| Platform | A small web app in TypeScript that runs on the local computer with one command (e.g. `pnpm start`) and opens at `http://localhost:<port>`. No login. |
| Runner | A background process inside the same local app, so a run continues if the browser tab is closed, but not if the app itself is stopped. |
| Sending messages to the bot | Fake Gupshup messages to the bot's webhook on salud-stage. Details are in doc 04, §4.2. Filling WhatsApp forms is not possible from outside today (doc 07, B3). The webhook is a public URL, so a local computer can reach it. |
| Storage | A local database file (SQLite) holding test cases, runs, results, conversations, Jira links and AI usage. Back it up or copy it to move the platform to another computer. |
| Secrets | Read-only salud-stage key, Claude API key, Jira token and Macena testing credentials go in a local `.env` file that is **never committed**, even though the repo is private. |
| AI | Claude API: writes and edits test cases, judges replies, explains failures, drafts Jira cards. Usage is recorded for the budget legend. |
| Jira | Jira Cloud REST API with an API token. Creates Bugs and Tasks, unassigned, and adds comments. Doesn't read status. |
| Code | A **private** repo, `qa-automatization-module`. |
| Later: hosting | Our own cloud account. If it's Google Cloud, it fits naturally next to the chatbot's Firebase projects. |

## 6. MVP is done when…

1. The platform starts locally with one command and opens in the browser.
2. Clicking **"Generate test cases"** produces at least **6 useful proposals**, covering
   greeting, booking, confirm from reminder, cancel from reminder, hand-over to a person, and
   messages the bot doesn't understand. Admins approve them without needing a developer.
3. An admin can write a test case in plain words, try it and save it.
4. An admin can start a run with one click and watch its progress.
5. The report shows each conversation, each check, the AI judge's opinion and a likely cause for failures.
6. The same Active tests give the **same result 9 times out of 10** when nothing changed in the bot.
7. A failed test can become a Jira Bug or Task in two clicks. Earlier cards for the same test are offered for a comment instead.
8. The AI budget legend shows this month's spend against the limit and enforces it.
9. Nothing ever runs outside salud-stage / the QA clinic.

| --- | --- |
| Jira | Bugs and Tasks · nobody assigned by default · no status sync in the MVP |
| Parallel runs | Not handled in the MVP (one run at a time) |

## 9. Known limits of the local MVP

1. **Only works while the computer is on** and the platform is running. Closing it stops a run.
2. **Only usable on that computer.** Other admins can't open it from their own machines. Reports and
   cards are shared through Jira, which is why the cards carry the whole conversation.
3. **The WhatsApp 24-hour rule.** WhatsApp lets a business send free-text messages to a person only
   within 24 hours of that person's last real message.
   - Our fake messages don't come from WhatsApp, so the bot's replies to the test phone may be
     **rejected by WhatsApp** if the phone hasn't really written to the QA bot number in the last 24 hours.
   - **Workaround:** before a test session, send a real "hola" from the test phone to the QA bot number.
   - **To verify in step 1:** does the bot still save its reply in the database when WhatsApp rejects
     delivery? If it does, tests pass either way, and only the human view on the phone is affected.
4. **One test phone, one patient.** All test cases share one patient identity. That's why runs go
   one at a time, and why each test starts by resetting that patient's conversation in the QA clinic.
5. **The budget legend is a few hours behind.** Anthropic's real cost figures arrive 4–24 hours late.
   The platform fills that gap with its own calls, but spend from other tools in those last
   hours shows up only when Anthropic's figures catch up. The Console spend limit remains the hard stop.
6. **No history of who did what.** There is no login, so runs and cards aren't tied to a person.
7. **Backups are manual.** All data lives in one local file.
