# Git standards — prestobots (Chatbot Testing Platform)

The rules every developer and agent follows when using git in this project. This document is the source of truth: the `/git-*` commands, the `git-advisor` subagent and the git hooks all apply it. Change a rule here first (and keep `.githooks/` in sync).

The git repository root is the folder above `prestobots/`; everything in the repository lives under `prestobots/`.

## Quick reference

| What           | Rule                     | Example                                 |
| -------------- | ------------------------ | --------------------------------------- |
| Branch         | `<type>/<description>`   | `feat/android-test-phones`              |
| Commit header  | `<type>[!]: <subject>`   | `feat: add android test phone channel`  |
| Merge          | Squash merge via pull request (PR title becomes the commit on `main`) | |
| Base branch    | `main`                   |                                         |

Valid branches: `feat/android-test-phones`, `fix/stage-reply-timeout`, `docs/git-standards`. Invalid: `feature/android-phones` (`feature` is not a type; use `feat`), `feat/Android_Phones` (uppercase and underscore; use lowercase kebab-case).

Valid commits: `feat: add android test phone channel`, `fix: stop the run when the google sign-in expires`, `feat!: replace the key file with google sign-in`. Invalid: `feature: add phones` (`feature` is not a type), `Fix stuff.` (no type, and ends with a period).

## Branching strategy

GitHub Flow. `main` is the only long-lived branch and is always in a working state. Every change starts on a short-lived branch created from an up-to-date `main` and goes back to `main` through a pull request, merged with squash.

## Branch naming

- Pattern: `<type>/<description>` — regex: `^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)/[a-z0-9]+(-[a-z0-9]+)*$`.
- Types (shared with commits):
  - `feat` — a new feature for the user or admin.
  - `fix` — a bug fix.
  - `docs` — documentation only (`docs/`, READMEs, specs).
  - `style` — formatting only, no behavior change.
  - `refactor` — code change that neither fixes a bug nor adds a feature.
  - `perf` — performance improvement.
  - `test` — adding or fixing tests only.
  - `build` — dependencies, package manager, build setup.
  - `ci` — continuous integration configuration.
  - `chore` — maintenance that fits no other type (tooling, config, housekeeping).
  - `revert` — reverts a previous change.
- Lowercase kebab-case, max 50 characters. No ticket references.
- The base branch (`main`) is never used for work.

## Commits

- Convention: Conventional Commits, without scope. Header: `<type>[!]: <subject>` — regex: `^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)!?: [^ ](.*[^.])?$`.
- Types: the same list as branch types. Scope: not used. Breaking changes: `!` after the type (`feat!: …`) and a `BREAKING CHANGE: <what changes and how to migrate>` footer.
- Language: English. Imperative mood ("add", not "added"). Subject ≤ 72 characters, no trailing period.
- Body: required for non-trivial changes, optional for trivial ones (typos, formatting, one-line fixes). Explain *why*, wrap at 72 characters. Footers: `BREAKING CHANGE:` only.
- Granularity: atomic — one logical change per commit. Work-in-progress commits are allowed on your own branch (they disappear with the squash merge), but they still follow the header format (e.g. `chore: wip android device manager`).
- AI-assisted commits: attribution trailers and lines are **forbidden**. No `Co-Authored-By:` line naming an AI tool and no "Generated with …" line, in commits or pull requests. Never bypass hooks (`--no-verify`).
- Messages generated by git itself (`Merge …`, `Revert "…"`, `fixup! …`, `squash! …`) are allowed.

## Pull requests

- Title: the commit header format (`<type>[!]: <subject>`), because it becomes the squash commit on `main`. Open a draft pull request while the work is in progress.
- Body sections: Summary, Changes, How to test, Related (the spec under `specs/`, when there is one).
- Before opening: `pnpm typecheck` and `pnpm test` pass in `app/`; the branch is up to date with `main` via rebase.
- Reviews: no approval required (single developer). Size: aim for ≤ 400 changed lines (excluding lockfiles); split larger work.

## Merging and history

- Merge strategy: squash merge — one commit per pull request keeps `main` readable and lets branches keep work-in-progress commits.
- Updating a branch with its base: rebase onto `main` (`git pull --rebase origin main` or `git rebase origin/main`).
- Protected branches: `main` — no direct pushes; everything goes through a pull request. Never force-push shared branches; `git push --force-with-lease` only on your own unmerged branch.
- Delete branches after merge: yes.

## Tags and versioning

No tags or versioning scheme.

## Setup (every developer, once per clone)

Run from the repository root (the folder above `prestobots/`):

```bash
git config --local pull.rebase true
git config --local fetch.prune true
git config --local push.autoSetupRemote true
git config --local init.defaultBranch main
git config --local core.hooksPath prestobots/.githooks
```

Signing commits (GPG or SSH) is recommended but not required.

## Enforcement

Git hooks in `prestobots/.githooks/`:
- `commit-msg` validates the commit header (format, types, length, no trailing period) and rejects AI attribution lines.
- `pre-push` validates branch names and blocks direct pushes to `main`.

## Commands

- `/git-branch` — create a branch from an up-to-date `main` with a compliant name.
- `/git-commit` — turn the current changes into commits with compliant messages.
- `git-advisor` subagent — reviews changes and proposes branch names, commit splits and messages, pull request text; never modifies the repository.
