# Constitution — prestobots

These principles override any spec or task instruction. Changing them requires explicit approval from the project owner.

Each article separates **Current practice** (what the code does today) from **For new and changed code** (rules adopted on 2026-11-23 that existing code may not follow yet).

## 1. Purpose
Let non-technical admins create, run and review test cases for the Cauce chatbot (`prestobotsv3`, product Salud) from a web page. Test cases can be written in plain words, generated by AI, judged by AI and reported to Jira. Out of scope for the MVP: testing production or real clinics, hosting, logins, multi-tenancy, and other products (see `docs/06-mvp-scope.md`).

**Direction (not adopted):** the longer-term goal is a sellable multi-tenant AI QA product (projects with a URL + repos, discovery, monitoring; possibly Next.js, Postgres, a job queue, Playwright workers). Any move toward it, including a stack change, needs its own spec approved by the owner.

## 2. Safety
- **Current practice:** the runner only targets `salud-stage`. `assertSafeTarget` (`packages/runner/src/stage/guard.ts`) checks the project, the credentials' project, the webhook host and the org. Firestore is only read. Fake message ids start with `qa-`. Jira cards never include the patient phone or any key.
- **For new and changed code:** these guards may be extended but never relaxed. Every new outbound integration gets an equivalent guard with tests.

## 3. Architecture
- **Current practice:** `packages/shared` holds the domain types as zod schemas and has no I/O. `packages/runner` talks to chatbots through the `Channel` interface (`channels/types.ts`). `packages/ai` is the only place that imports `@anthropic-ai/sdk`. `apps/server` is the only place that reads env (`src/config.ts`) and touches SQLite (`src/db.ts`). Packages receive settings as parameters. `apps/web` talks to the server only through `/api`.
- **For new and changed code:** keep these boundaries. New chatbot targets are new `Channel` implementations. New LLM uses go in `packages/ai` with cost tracking and budget checks.

## 4. Dependencies
- **Current practice:** few, mainstream dependencies (Fastify, better-sqlite3, zod, firebase-admin, Anthropic SDK, React, TanStack Query, Tailwind).
- **For new and changed code:** minimal. Each new dependency is justified in the spec's plan (why the stdlib or an existing dependency isn't enough) before it is added.

## 5. Data
- **Current practice:** one local SQLite file (`app/data/platform.db`). Each row stores the full object as JSON, validated with the `packages/shared` schemas on read, plus a few columns for filtering. The schema is created with `CREATE TABLE IF NOT EXISTS` in `apps/server/src/db.ts`, and there are no migrations. Data and secrets are never committed.
- **For new and changed code:** changes to a shared schema or a table are a spec decision and must stay readable for existing rows (optional fields or defaults), or ship with a migration step.

## 6. Quality
- **Test-first (TDD):** every behavior change starts with a test that fails for the expected reason (red), then the minimum code to make it pass (green), then refactoring with all tests green. Only setup, configuration, documentation and manual checks are exempt.
- **Current practice:** Vitest tests cover `apps/server`, `packages/runner` and `packages/ai`. Tests use the demo bot and fakes, never the real chatbot or the paid API. `apps/web` and `packages/shared` have no tests.
- **For new and changed code:** logic in any package, including `apps/web` and `packages/shared`, ships with Vitest tests. A task is done only when `pnpm typecheck` and `pnpm test` pass in `app/`.
- **Targets (future specs):** adopt Biome for formatting and linting, configured to match the current style. Add CI (install, typecheck, test, lint) later.

## 7. Conventions
- **Current practice:** TypeScript strict + `noUncheckedIndexedAccess`, ESM, `.ts` import extensions, arrow functions, zod at every boundary, errors with plain-language messages. 2 spaces, single quotes, semicolons, es5 trailing commas. Identifiers, comments and UI text are in English, written for non-technical admins. Test stories and bot texts are in Spanish.
- **For new and changed code:** same rules. User-facing text explains what happened and what to do, without jargon.

## 8. Workflow
Spec first: every feature or behavior change starts with a spec folder `specs/NNN-<slug>/` holding `spec.md` (WHAT/WHY), `plan.md` (HOW) and `tasks.md` (the ordered implementation checklist), based on `specs/_templates/`. Only one spec is `Active` at a time and code follows its spec, plan and tasks; if reality diverges, update the spec before the code.
